# Tenet 엔지니어링 원칙 v1 초안

## 목적

Tenet은 개발, 수정, 리팩터링, 기존 코드 검토에서 동일한 설계 판단을 사용합니다.
이 문서는 특정 프레임워크를 강요하는 규칙집이 아니라, 근거를 가지고 선택하는 기본 원칙입니다.

각 원칙은 다음 세 가지 관점을 갖습니다.

- **개발**: 작업할 때 무엇을 우선해야 하는가
- **검토**: 기존 코드에서 어떤 증거를 확인해야 하는가
- **주의**: 원칙을 형식적으로 적용하여 발생하는 오판은 무엇인가

## Domain

### 1. Model the Real Domain — 실제 도메인을 모델링합니다

- 개발: 요구사항과 업무 규칙을 파악하고 데이터 구조와 동작으로 표현합니다.
- 검토: 중요한 비즈니스 결정이 어디에 구현되어 있는지 추적합니다.
- 주의: 간단한 유틸리티나 CRUD 처리에 불필요한 도메인 계층을 강요하지 않습니다.

### 2. Keep a Shared Language — 문맥 안에서 용어를 일치시킵니다

- 개발: 도메인 전문가와 합의한 개념을 코드, 테스트, 문서에 일관되게 사용합니다.
- 검토: 같은 용어가 충돌하거나 서로 다른 뜻의 용어가 무분별하게 혼합되는지 확인합니다.
- 주의: 서로 다른 Bounded Context가 반드시 같은 용어와 모델을 사용해야 하는 것은 아닙니다.

### 3. Protect Invariants — 도메인 불변식을 보호합니다

- 개발: 허용되는 상태와 상태 전환을 정의하고 잘못된 변경을 차단합니다.
- 검토: 규칙 위반이 가능한 경로와 규칙이 중복 구현된 위치를 근거로 확인합니다.
- 주의: 타입만으로 표현할 수 없는 조건은 명시적인 도메인 검증이나 트랜잭션이 필요할 수 있습니다.

### 4. Respect Model Boundaries — 모델의 책임과 경계를 존중합니다

- 개발: 비즈니스 책임을 구분하고 외부 입력·인프라 의존성과의 경계를 명확히 합니다.
- 검토: 도메인 규칙이 여러 계층에 분산되거나 문맥 간 모델이 무단으로 새어 나가는지 봅니다.
- 주의: Bounded Context를 폴더, 서비스, Aggregate와 동일한 개념으로 취급하지 않습니다.

## Testing

### 5. Define Behavior Before Coding — 구현 전에 기대 동작을 정의합니다

- 개발: 다음 작은 변경의 성공·실패 조건을 명시하고, 새 동작은 먼저 실패하는 테스트로 표현합니다.
- 검토: 관찰 가능한 계약과 실제 테스트가 있는지 판단합니다.
- 주의: 완성된 코드만 보고 테스트 작성 순서를 추정하거나 TDD 미준수라고 단정하지 않습니다.

### 6. Follow Red–Green–Refactor — 실패·통과·정리 주기를 따릅니다

- 개발: 테스트의 예상 실패를 확인하고 최소 코드로 통과시킨 뒤, 검증을 유지하며 정리합니다.
- 검토: 개발 이력이 남아 있다면 단계적 검증 증거를 확인하고, 없으면 현재 테스트의 효력을 살핍니다.
- 주의: 실행 가능한 테스트가 현실적으로 불가능하다면 형식적 테스트를 만들지 않고 이유를 설명합니다.

### 7. Test Behavior and Meaningful Failures — 행동과 중요한 실패를 검증합니다

- 개발: 사용자가 관찰할 수 있는 결과와 도메인 규칙의 정상·오류·경계 조건을 테스트합니다.
- 검토: 테스트가 구현 내부 호출이나 Mock 상호작용만 확인하고 실제 결과를 놓치지 않는지 봅니다.
- 주의: 높은 커버리지, 변이 점수 또는 테스트 개수만으로 정확성을 보장한다고 주장하지 않습니다.

## Design

### 8. Make Dependencies and State Explicit — 의존성과 상태를 드러냅니다

- 개발: 경계에서 입력을 검증하고 부작용, 재시도, 공유 가변 상태를 적절하게 다룹니다.
- 검토: 숨은 의존성, 경쟁 상태, 중복 실행 시 부작용, 비즈니스 로직과 인프라의 결합을 확인합니다.
- 주의: 멱등성이나 동시성 제어가 필요하지 않은 순수 연산에 불필요한 장치를 추가하지 않습니다.

### 9. Subtract Before You Add — 추가하기 전에 단순화합니다

- 개발: 해결할 문제에 필요한 최소 변경을 적용하고 중복 추상화나 선행 일반화를 피합니다.
- 검토: 중복된 결정, 불필요한 간접 계층, 과도한 복잡성을 구체적인 유지보수 비용과 연결합니다.
- 주의: 코드가 비슷해 보인다는 이유만으로 서로 다른 도메인 의미를 억지로 통합하지 않습니다.

## Evolution

### 10. Change With Evidence — 근거를 가지고 안전하게 변경합니다

- 개발: 실패를 재현하고 원인을 해결하며, 작은 검증 단위로 변경하고 회귀 테스트를 유지합니다.
- 검토: 발견한 문제에 재현 경로, 코드 위치, 영향, 확인 방법이 있는지 검증합니다.
- 주의: 관찰된 결함과 개인적인 설계 선호, 아직 확인하지 못한 가설을 구분합니다.

## 적용 규칙

### 개발 및 수정

1. 저장소의 기존 설계와 실제 요구사항을 먼저 확인합니다.
2. 도메인과 성공 조건을 명확히 한 후 작은 행동 단위로 진행합니다.
3. 새 동작은 TDD를 기본값으로 사용합니다. 테스트를 실행할 수 없는 사유는 드러냅니다.
4. 기존 기능의 동작을 보존해야 한다면 회귀 테스트나 특성화 테스트를 우선 고려합니다.
5. 사용자가 요청한 범위를 벗어나는 코드 변경, 의존성 추가, 커밋·푸시는 임의로 하지 않습니다.

### 코드 및 저장소 검토

1. 실행 흐름과 도메인 경계를 파악하고 코드·테스트·문서에서 근거를 확보합니다.
2. 실제로 잘못 동작할 수 있는 **결함**과 선택 가능한 **개선 제안**을 구분합니다.
3. 요구사항이나 테스트 실행 결과를 확인할 수 없으면 **확인 불가**로 남깁니다.
4. 소스 파일과 위치, 문제 조건, 예상 영향, 가능한 검증 방법을 기록합니다.
5. 검토를 요청받은 경우 명시적 허가 없이 파일을 수정하거나 PR을 만들지 않습니다.

### 원칙 사이의 충돌

- 기존의 올바른 동작과 명시된 비즈니스 불변식을 우선 보호합니다.
- 근거 없는 큰 재설계보다 작고 검증 가능한 변경을 선택합니다.
- 단순성과 도메인 충실성이 충돌하면 실제 도메인 복잡성을 숨기지 않습니다.
- 프로젝트가 이미 사용하는 품질 도구와 기준은 존중하되 보편적 의무로 일반화하지 않습니다.
- 정보가 부족한 경우에는 추측으로 원칙 위반을 확정하지 않습니다.

## 도구와 종속성

Tenet의 기본 동작은 외부 저장소 체크아웃이나 특정 분석 도구를 요구하지 않습니다.

- 복잡도·커버리지 도구는 유지보수 위험을 살피는 보조 자료입니다.
- 구조적 중복 탐지는 리팩터링 후보를 찾는 수단이지 제거 의무가 아닙니다.
- 변이 테스트는 검증이 약한 테스트를 찾아내는 수단이지 만능 품질 증명이 아닙니다.
- 다이어그램 도구는 경계를 이해하는 데 유용할 수 있지만 필수는 아닙니다.
