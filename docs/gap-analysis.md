# Tenet 원칙 비교 및 보완 분석

## 목적

[원본 조사](ub-mode-audit.md)에 기록된 소프트웨어 설계·테스트·작업 절차를
개발과 코드 검토에 공통으로 적용할 수 있는 원칙으로 재구성합니다.
아래 영문 명칭은 비교 대상의 원래 항목 이름이며, Tenet 사용자가 알아야 할 명령어나 외부 의존성이 아닙니다.
이 문서는 변경 결정을 기록하며, 실제 실행 지침은 Skill에서 정의합니다.

## 분류 기준

- **유지**: 원칙의 목적을 그대로 살리고 문장을 새로 작성합니다.
- **수정**: 목적은 유지하되 적용 조건, 작업 모드, 검증 기준을 변경합니다.
- **제외**: 공통 설계 원칙이 아니므로 기본 스킬에서는 강제하지 않습니다.
- **추가**: DDD·TDD의 중요한 부분이지만 원본에 직접적인 지침이 부족한 영역입니다.

## 원본 항목별 분류

| 기존 지침(원래 명칭) | 판단 | 일반화한 의미와 적용 방향 |
| --- | --- | --- |
| Laziness Protocol | 유지 | 필요한 최소 변경, 중복된 정책 결정 방지 |
| Foundational Thinking | 수정 | 데이터 구조와 실제 도메인 전제 먼저 확인 |
| TDD | 수정 | 새 동작은 테스트 우선, 기존 코드 검토는 증거 중심 |
| Redesign From First Principles | 수정 | 잘못된 설계 전제는 재검토하되 무조건 재설계 금지 |
| Attack the Premise | 수정 | 반복 실패할 때 전제 자체를 재검증 |
| Subtract Before You Add | 유지 | 추가 전에 복잡성을 줄일 방법 확인 |
| Outcome-Oriented Execution | 유지 | 관찰 가능한 성공 조건 정의 |
| Build the Lever | 제외 | 전용 도구 제작은 선택적 실행 전략 |
| Model the Domain | 수정 | 도메인 언어, 경계, 책임과 불변식 보강 |
| Boundary Discipline | 수정 | 도메인 경계와 시스템 입출력 경계 구분 |
| Type System Discipline | 수정 | 언어에서 가능한 수준으로 잘못된 상태 방지 |
| Make Operations Idempotent | 수정 | 재시도·중복 실행이 가능한 작업에 적용 |
| Separate Before Serializing Shared State | 수정 | 공유 가변 상태에 실제 동시성 위험이 있는 경우 적용 |
| Fix Root Causes | 유지 | 증상보다 재현된 원인 해결 |
| Sequence Work into Verifiable Units | 유지 | 작은 변경과 검증의 반복 |
| Test Behavior, Not Implementation | 유지 | 외부에서 관찰 가능한 계약 검증 |
| 복잡도·커버리지 평가(Crapper) | 수정 | 변경 위험도를 참고하되 특정 도구나 점수는 강제하지 않음 |
| 코드 중복 분석(Dryer) | 수정 | 기능과 도메인 의미를 고려해 중복을 검토하고 수치 기준은 강제하지 않음 |
| 변이 테스트(Mutator) | 수정 | 테스트가 잘못된 구현을 탐지하는지 검토하되 도구 설치는 강제하지 않음 |
| Refactoring | 유지 | 동작 보존을 확인하며 구조 개선 |
| Keep a Log | 제외 | 상세 작업 로그 강제는 공통 설계 원칙 아님 |
| Guard the Context Window | 제외 | 에이전트별 운영 전략 |
| Worktree Cleanup | 제외 | 사용 환경에 의존하는 절차 |
| Commit and Push | 제외 | Git 변경은 별도 사용자 권한에 따른 작업 |

## DDD 관점에서 추가할 사항

1. **공통 언어(Ubiquitous Language)**: 코드, 테스트, 문서에서 해당 문맥의 도메인 용어를 일관되게 사용합니다.
2. **모델 경계**: 같은 용어도 문맥에 따라 의미가 다른지 구분합니다.
3. **불변식과 책임**: 도메인 규칙을 책임이 있는 모델이나 서비스에 둡니다.
4. **적정한 모델링**: Entity, Value Object, Aggregate는 필요한 경우에만 도입합니다.
5. **검토의 불확실성**: 코드에서 추론한 규칙과 명시된 요구사항을 구분합니다.

Bounded Context는 디렉터리나 마이크로서비스와 일대일로 대응하는 개념이 아닙니다.
업무 개념과 언어가 일관되게 정의되는 모델의 경계입니다.

## TDD 관점에서 추가할 사항

1. **새 동작 구현**: 테스트가 기대한 이유로 실패하는지 확인하고, 최소 구현 후 정리합니다.
2. **기존 코드 변경**: 보존할 계약을 파악하고 필요한 경우 특성화 테스트를 작성합니다.
3. **검토 시 판단**: 테스트가 구현보다 먼저 작성되었는지 결과 코드만으로 단정하지 않습니다.
4. **테스트의 효력**: 주요 정상·실패·경계 조건을 보호하는지 살핍니다.
5. **도구 독립성**: 커버리지와 변이 점수는 보조 증거입니다. 수치 하나로 품질을 확정하지 않습니다.

## 공통 원칙의 초안 범주

| 범주 | 다룰 문제 | 개발과 검토의 공통 질문 |
| --- | --- | --- |
| Domain | 모델, 용어, 경계, 불변식 | 도메인 규칙이 올바르게 표현되고 보호되는가? |
| Testing | 테스트 우선, 행동, 회귀, 실패 조건 | 검증이 사용자 동작과 중요한 규칙을 지키는가? |
| Design | 단순성, 의존성, 중복, 상태 | 구조가 실제 요구사항에 비해 불필요하게 복잡한가? |
| Evolution | 근본 원인, 소규모 변경, 리팩터링 | 변경의 이유와 결과를 증명할 수 있는가? |

## 적용과 평가의 구분

- **개발**: 앞으로 작성할 동작을 먼저 명세하고 가능한 경우 TDD 주기를 따릅니다.
- **리팩터링**: 기존 동작을 보호하는 증거를 확보한 뒤 구조를 바꿉니다.
- **검토**: 실제로 확인한 코드와 테스트에 근거해 결함과 제안을 구분합니다.
- **공통**: 사용자가 요청하지 않은 아키텍처, 의존성, 변경 범위를 강요하지 않습니다.

DDD와 TDD는 서로를 대체하지 않습니다. 도메인 모델의 정확성과
테스트의 검증 능력을 함께 살피되 서로 다른 판단 기준을 유지합니다.

## 다음 단계에서 결정할 사항

- 원칙을 정확히 10개로 제한하지 않습니다. 중복을 합치고 빠진 부분만 추가합니다.
- 각 원칙에 적용 조건, 검증 가능한 증거와 남용 방지 조건을 명시합니다.
- 분석 도구와 점수는 선택적입니다. 프로젝트 고유 기준이 있으면 이를 우선합니다.
- 검토 시 `발견된 결함`, `개선 제안`, `확인 불가`를 구분합니다.
- 작업 진행 방식이나 PR 운영 방식은 도메인·테스트 원칙과 구분합니다.
